## Change tracking fundamentals

### How EF Core detects changes

When you load an entity via a tracked query, EF Core takes a **snapshot** of its property values at load time. When `SaveChanges` is called (or when EF needs to check state), it runs `DetectChanges`, which compares current property values against the snapshot to determine what has changed.

Entity states:
| State | Meaning | SQL generated |
|-------|---------|---------------|
| `Added` | New entity, not yet in the database | `INSERT` |
| `Modified` | Tracked entity whose properties have changed | `UPDATE` (changed columns only) |
| `Deleted` | Entity scheduled for removal | `DELETE` |
| `Unchanged` | Tracked entity with no changes | none |
| `Detached` | Entity not known to the current context | none |

```csharp
// Inspect entity state explicitly.
var order = await db.Orders.FindAsync([id], ct);
Console.WriteLine(db.Entry(order!).State); // EntityState.Unchanged

order!.Status = OrderStatus.Shipped;
Console.WriteLine(db.Entry(order).State);  // EntityState.Modified (after DetectChanges)
```

### DetectChanges behavior

`DetectChanges` runs automatically before `SaveChanges`, before queries (to ensure the identity map is consistent), and in some other internal paths. For tight loops, this can be a performance concern:

```csharp
// Disable automatic DetectChanges when bulk-adding many entities.
db.ChangeTracker.AutoDetectChangesEnabled = false;
try
{
    foreach (var item in largeCollection)
    {
        db.Products.Add(item); // Adding does not require DetectChanges.
    }
    await db.SaveChangesAsync(ct);
}
finally
{
    db.ChangeTracker.AutoDetectChangesEnabled = true;
}
```

Only disable `AutoDetectChangesEnabled` when you understand the implications — you become responsible for ensuring the tracker is in a correct state before save.

## SaveChanges patterns

### Batching

EF Core batches multiple DML statements into a single round trip. Inserting 100 entities calls `SaveChanges` once, not 100 times:

```csharp
// One round trip for all inserts.
db.Orders.AddRange(newOrders);
await db.SaveChangesAsync(ct);
```

EF Core uses a configurable batch size (`MaxBatchSize` per provider defaults). SQL Server defaults to 42 statements per batch; PostgreSQL defaults to unlimited.

```csharp
// Tune per provider if needed.
options.UseSqlServer(connStr, sql => sql.MaxBatchSize(100));
```

### Return values

After `SaveChanges`, EF Core populates database-generated values back onto the entity:
- Primary keys generated by the database (`IDENTITY`, sequences, `uuid_generate_v4()`).
- Computed columns marked with `ValueGeneratedOnAddOrUpdate`.
- Concurrency tokens set by the database (row versions, timestamps).

```csharp
var order = new Order { CustomerId = 42, Total = 99.99m };
db.Orders.Add(order);
await db.SaveChangesAsync(ct);

// order.Id is now populated with the database-generated key.
Console.WriteLine(order.Id);
```

### SaveChanges in a loop is an anti-pattern

Each `SaveChanges` call is a round trip and a transaction. Calling it inside a loop serializes work that could be batched:

```csharp
// SLOW — one transaction per item.
foreach (var item in items)
{
    db.Items.Add(item);
    await db.SaveChangesAsync(ct); // avoid this
}

// FAST — one transaction, one or a few round trips.
db.Items.AddRange(items);
await db.SaveChangesAsync(ct);
```

For very large collections (tens of thousands of rows), consider chunking to avoid holding a single transaction open too long:

```csharp
const int chunkSize = 500;
foreach (var chunk in items.Chunk(chunkSize))
{
    db.Items.AddRange(chunk);
    await db.SaveChangesAsync(ct);
    db.ChangeTracker.Clear(); // release tracked entities to keep memory flat
}
```

## Bulk operations (EF7+, extended in EF10)

EF Core 7 introduced `ExecuteUpdate` and `ExecuteDelete` for set-based operations that do not require loading entities into memory.

### ExecuteUpdate

Updates matching rows directly in the database:

```csharp
// UPDATE Orders SET Status = 2, UpdatedAt = @now WHERE CustomerId = @id
await db.Orders
    .Where(o => o.CustomerId == customerId && o.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(s => s
        .SetProperty(o => o.Status, OrderStatus.Cancelled)
        .SetProperty(o => o.UpdatedAt, DateTimeOffset.UtcNow),
        ct);
```

#### Conditional setters (EF Core 10+)

EF Core 10 added an `ExecuteUpdateAsync` overload that takes a plain (non-expression) lambda, so setters can be applied with ordinary control flow instead of a fixed chain:

```csharp
// EF Core 10+ — build the setter list conditionally.
await db.Orders
    .Where(o => o.CustomerId == customerId)
    .ExecuteUpdateAsync(s =>
    {
        s.SetProperty(o => o.Status, OrderStatus.Cancelled);
        if (reasonChanged)
        {
            s.SetProperty(o => o.CancelReason, reason);
        }
    }, ct);
```

On EF Core 7–9 only the chained-expression form above exists; branch by issuing separate `ExecuteUpdateAsync` calls instead.

### ExecuteDelete

Deletes matching rows directly:

```csharp
// DELETE FROM AuditLogs WHERE CreatedAt < @cutoff
await db.AuditLogs
    .Where(l => l.CreatedAt < cutoff)
    .ExecuteDeleteAsync(ct);
```

### When to use vs traditional load-modify-save

Use `ExecuteUpdate`/`ExecuteDelete` when:
- You do not need to inspect or validate individual entities before changing them.
- The operation is purely set-based (no per-row business logic).
- You want maximum performance at scale (no entity materialization or change tracking).

Use traditional load-modify-save when:
- Domain logic must run on each entity (validation, raising domain events).
- You need the generated/computed values back after the operation.
- The operation must trigger EF interceptors or `SaveChanges` events.

Limitations of bulk operations:
- Changes bypass the change tracker — no `EntityState` transitions, no interceptors, no `SavingChanges` event.
- No cascading deletes through EF navigation fixup.
- The count of affected rows is returned, but individual entity state is not available.
- EF does not refresh in-memory tracked entities after `ExecuteUpdate`/`ExecuteDelete`; if you have already loaded entities, they may be stale.

## Concurrency control

EF Core uses **optimistic concurrency** — it does not lock rows on read; instead, it checks at save time whether the row was modified by another process since it was loaded. If it was, `DbUpdateConcurrencyException` is thrown.

### Configuring a concurrency token

**Option 1: [ConcurrencyCheck] attribute** on any property:
```csharp
public sealed class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;

    [ConcurrencyCheck]
    public decimal Price { get; set; }
}
```
EF adds the original price value to the `WHERE` clause: `UPDATE Products SET Price = @new WHERE Id = @id AND Price = @original`.

**Option 2: Row version / timestamp** — a database-managed binary stamp that changes on every update (SQL Server `rowversion`, PostgreSQL `xmin`):

```csharp
public sealed class Order
{
    public int Id { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = [];
}
```

Fluent API equivalent:
```csharp
modelBuilder.Entity<Order>()
    .Property(o => o.RowVersion)
    .IsRowVersion(); // provider-specific; maps to rowversion on SQL Server
```

### Handling DbUpdateConcurrencyException

Three strategies when a conflict is detected:

**Strategy 1: Client wins (overwrite store)**
```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        // Reload the current database values to update the concurrency token,
        // then save again — our proposed values are kept.
        var dbValues = await entry.GetDatabaseValuesAsync(ct);
        if (dbValues is null)
        {
            // Row was deleted — decide whether to re-insert or abort.
            throw;
        }
        entry.OriginalValues.SetValues(dbValues); // update the token
    }
    await db.SaveChangesAsync(ct); // second save succeeds
}
```

**Strategy 2: Store wins (discard client changes)**
```csharp
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        var dbValues = await entry.GetDatabaseValuesAsync(ct);
        if (dbValues is null) throw; // row deleted — cannot recover silently

        // Reload current values; discard what the client tried to set.
        entry.CurrentValues.SetValues(dbValues);
        entry.OriginalValues.SetValues(dbValues);
    }
    // Do not re-save; return the current DB state to the caller.
}
```

**Strategy 3: Merge (manual per-property resolution)**
```csharp
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var proposed = entry.CurrentValues;
    var db_ = await entry.GetDatabaseValuesAsync(ct);
    var original = entry.OriginalValues;

    // Example: keep our Status change, accept the database's Price.
    proposed["Status"] = proposed["Status"];   // client wins for Status
    proposed["Price"] = db_!["Price"];          // store wins for Price
    entry.OriginalValues.SetValues(db_!);

    await db.SaveChangesAsync(ct);
}
```

## Disconnected entities

In web scenarios, entities often travel outside the context boundary (e.g., serialized to JSON, returned in an HTTP response, then sent back in a PUT request). The entity is "disconnected" — the new context has no knowledge of it.

### Attach vs Update vs Add

```csharp
// Scenario: entity came from a PUT body; we do not know what changed.

// Add — treats the entity as entirely new; generates INSERT.
db.Orders.Add(existingOrder); // wrong for an update scenario

// Attach — marks entity as Unchanged; no SQL unless you then modify properties.
db.Orders.Attach(existingOrder);
// Manually mark modified:
db.Entry(existingOrder).State = EntityState.Modified;

// Update — marks all scalar properties as Modified; generates UPDATE for every column.
db.Orders.Update(existingOrder); // convenient but sends all columns, not just changed ones
```

For precise updates (only columns that actually changed), load the original from the database and apply the incoming values:

```csharp
public async Task UpdateOrderAsync(OrderUpdateDto dto, CancellationToken ct)
{
    var order = await db.Orders.FindAsync([dto.Id], ct)
        ?? throw new InvalidOperationException($"Order {dto.Id} not found.");

    // Apply only the fields the client is allowed to change.
    order.Status = dto.Status;
    order.Notes = dto.Notes;

    // SaveChanges sends UPDATE with only the two changed columns.
    await db.SaveChangesAsync(ct);
}
```

### Graph tracking with TrackGraph

For complex disconnected object graphs (parent + children returned from a client):

```csharp
db.ChangeTracker.TrackGraph(rootEntity, node =>
{
    // Decide state per node based on a convention — e.g., Id == 0 means Added.
    node.Entry.State = node.Entry.IsKeySet
        ? EntityState.Modified
        : EntityState.Added;
});
await db.SaveChangesAsync(ct);
```

### Pitfall: attaching already-tracked entities

If you call `Attach` or `Update` on an entity whose key is already in the change tracker, EF throws `InvalidOperationException`. This happens when you load an entity in one path and then try to attach a separate instance with the same key:

```csharp
var loaded = await db.Orders.FindAsync([42], ct); // tracked
var detached = new Order { Id = 42, Status = OrderStatus.Shipped };
db.Orders.Update(detached); // throws — Id 42 is already tracked
```

Fix: either work with the already-tracked instance, or use a fresh context.

## Transactions

### Default SaveChanges transaction

`SaveChanges` wraps all batched operations in a single database transaction automatically. If any operation fails, the transaction rolls back. This is sufficient for most scenarios.

### Explicit transactions

Use an explicit transaction when you need to coordinate multiple `SaveChanges` calls or mix EF operations with raw SQL:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
try
{
    db.Orders.Add(newOrder);
    await db.SaveChangesAsync(ct);

    // Raw SQL that must be in the same transaction.
    await db.Database.ExecuteSqlInterpolatedAsync(
        $"UPDATE Inventory SET Stock = Stock - {quantity} WHERE ProductId = {productId}",
        ct);

    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}
```

### Execution strategies and retries

Transient failures (network blips, connection pool exhaustion) are common with cloud databases. EF Core providers include execution strategies that retry automatically:

```csharp
options.UseSqlServer(connStr, sql =>
    sql.EnableRetryOnFailure(
        maxRetryCount: 5,
        maxRetryDelay: TimeSpan.FromSeconds(10),
        errorNumbersToAdd: null));
```

Execution strategies do not work transparently with explicit transactions because retrying a failed transaction would re-execute operations that may have partially succeeded. Use `ExecuteInTransactionAsync` instead:

```csharp
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteInTransactionAsync(
    db,
    async (context, ct_) =>
    {
        context.Orders.Add(newOrder);
        await context.SaveChangesAsync(ct_);
        await context.Database.ExecuteSqlInterpolatedAsync(
            $"UPDATE Inventory SET Stock = Stock - {quantity} WHERE ProductId = {productId}",
            ct_);
    },
    async (context, ct_) =>
    {
        // Verification predicate: return true if the transaction already succeeded
        // (used to avoid a duplicate commit on retry).
        return await context.Orders.AnyAsync(o => o.IdempotencyKey == key, ct_);
    },
    ct);
```

### TransactionScope considerations

`TransactionScope` works with EF Core but requires async-friendly construction and can escalate to a distributed transaction (MSDTC) if multiple connections are enlisted. Prefer `BeginTransactionAsync` for new code. If `TransactionScope` is needed (legacy integration), always use `TransactionScopeAsyncFlowOption.Enabled`:

```csharp
using var scope = new TransactionScope(
    TransactionScopeOption.Required,
    new TransactionOptions { IsolationLevel = IsolationLevel.ReadCommitted },
    TransactionScopeAsyncFlowOption.Enabled);  // required for async/await

db.Orders.Add(order);
await db.SaveChangesAsync(ct);

scope.Complete();
```
